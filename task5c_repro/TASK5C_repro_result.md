# TASK5-C. CNN 제출 파이프라인 재현성 확인 — 결과

작성: 2026-07-23 (클로드코드 실행)

## 결과: 재현 성공, 학습/추론 분리 완료
- `train_cnn_production.py`: 2022~2024 전체 train(26,197행, 그리드매칭 100%)으로 1회 학습(조기종료=
  내부 시간순 마지막 10%, production 방식), seed=42. 체크포인트(`cnn_production_s42.pt`)만 저장.
- `infer_cnn_production.py`: 체크포인트 로드 → 실제 test 격자(`data/ldaps_test.csv`, `data/gfs_test.csv`,
  8760행) 예측 → `submission_ficr_w1_v7.csv`와 w=0.20 블렌드 → `submission_ficr_w1_v7_cnn_repro.csv` 저장.
- sanity: 결측 0 / 음수 0 / cap초과 0. v7 단독 대비 전체 8760행이 변경(행별 평균 절대차 213~390),
  블렌드가 실제로 작동함을 확인.

## 버그 발견·수정 (2차 산출물에 중요)
`_nan_to_med`(NaN→중앙값 대체 함수)가 **채널축이 아닌 축을 순회**하는 버그를 팀원 원본 코드
(`spatial_cnn_v7_top.py`, `v7_cnn_submission.py`) 둘 다에서 발견 — 두 파일이 서로 다른 방식으로
틀려 있었음(하나는 H축 순회, 하나는 flatten 후 잘못된 열 순회). train 격자에는 NaN이 전혀 없어서
(`cnn_gate/grid_tensors_cache.pkl` 검증: LDAPS/GFS 둘 다 NaN 0개) TASK1~4A 결과에는 전혀 영향 없음
(버그 코드경로 자체가 한 번도 실행 안 됨). **test 격자에는 NaN 752개 존재**(LDAPS 4×4×30×8760 중
0.018%) — 이번 TASK5-C에서 처음으로 실제 추론을 돌리며 노출됨.
- 우리 버전(`cnn_common.py`): 이 버그로 즉시 크래시(IndexError) — 수정 완료(채널축 올바르게 순회).
- 팀원 원본(`v7_cnn_submission.py`): 크래시는 안 나지만 imputation이 사실상 무의미하게 작동, 대신
  하류의 `mask=~isnan(cnn_vals)` 로직이 NaN 발생 행을 v7 단독값으로 자동 폴백시켜 **결과적으로는
  안전**했을 것으로 추정(크래시도 결측 누출도 없었을 것). 다만 그 ~752개 셀이 걸친 행들은 원래 의도한
  CNN 보정을 못 받고 조용히 순수 v7로 처리됐을 가능성 — LB 0.65184에 미미하지만 실재하는 영향 가능.
  (팀원 실제 제출 파일이 없어 검증 불가, 추정에 그침 — 판정에는 미사용.)

## 결론
cnn_gate/ 이식본만으로 학습·추론이 완전히 분리된 형태로 CNN 멤버를 처음부터 재현 가능함을 확인.
8/17 2차 산출물 코드 요건 충족. 팀원의 원본 checkpoint/데이터 없이도 우리 환경에서 동등한 파이프라인
독립 재현 가능(다만 우리가 고친 NaN 버그로 인해 팀원 실제 제출본과 픽셀 단위로 동일하지는 않을 수 있음 —
차이는 원본 버그의 영향을 받았을 소수 행에 국한, 방향은 "우리 쪽이 더 정확").
